# Branch-Based Versioning Specification

## Overview

This document specifies a branch-based versioning system for the cuddly-disco application that enables engineers to deploy and test their changes in the dev environment before merging to main. Each feature branch can deploy independent versions of the frontend and/or backend applications, accessible via header-based routing.

## Goals

1. **Per-App Deployment**: Deploy only the apps that have changed (frontend, backend, or both)
2. **Version Identification**: Clear naming convention using branch names for version identification
3. **Header-Based Access**: Access different versions using HTTP headers (`X-Version`)
4. **Automated Lifecycle**: Auto-deploy on push, auto-cleanup on merge/delete
5. **Future Prod Promotion**: Design with prod multi-versioning in mind for future implementation

## Design Decisions

Based on analysis and requirements gathering:

- **Version Naming**: `vX.X.X-<branch-name>` (e.g., `v1.3.0-add-user-auth`)
  - Base version (`vX.X.X`) comes from latest Git tag on main branch
  - Branch name sanitized: remove type prefix (feature/, bugfix/), replace special chars with hyphens
  - Examples:
    - `feature/add-user-auth` → `v1.3.0-add-user-auth`
    - `bugfix/fix-api-timeout` → `v1.3.0-fix-api-timeout`
    - `PROJ-123/implement-feature` → `v1.3.0-PROJ-123-implement-feature`

- **Deployment Trigger**: Every push to non-main branches
  - Immediate feedback for developers
  - No manual workflow_dispatch required
  - CI detects which apps changed and builds only those

- **Cleanup Policy**: Immediate cleanup on branch merge or delete
  - GitHub Actions workflow triggered on `pull_request: closed` or `delete: branch`
  - Removes Helm values files from Git
  - ArgoCD auto-prunes Kubernetes resources
  - Container images can optionally be deleted or kept for audit/rollback

## Technical Architecture

### 1. CI/CD Workflow Changes

#### New Workflow: Branch Container Build

**File**: `.github/workflows/ci.yml`

**Trigger Conditions**:
```yaml
on:
  push:
    branches-ignore:
      - main
  pull_request:
    types: [opened, synchronize, reopened]
```

**Workflow Jobs**:

1. **detect-changes** (new job)
   - Uses `paths` filter or `git diff` to detect which apps changed
   - Outputs: `frontend_changed`, `backend_changed`
   - Compares against main branch: `git diff origin/main...HEAD --name-only`
   - Logic:
     - Changes in `apps/frontend/**` → frontend_changed=true
     - Changes in `apps/backend/**` → backend_changed=true
     - Changes in both → both=true

2. **get-version-info** (new job)
   - Fetches latest Git tag from main branch: `git describe --tags --abbrev=0 origin/main`
   - Sanitizes branch name:
     ```bash
     # Remove refs/heads/ prefix
     BRANCH=${GITHUB_REF#refs/heads/}
     # Remove feature/, bugfix/, hotfix/ prefixes
     BRANCH=${BRANCH#feature/}
     BRANCH=${BRANCH#bugfix/}
     BRANCH=${BRANCH#hotfix/}
     # Replace special characters with hyphens
     BRANCH=$(echo "$BRANCH" | sed 's/[^a-zA-Z0-9-]/-/g' | sed 's/--*/-/g' | tr '[:upper:]' '[:lower:]')
     ```
   - Outputs: `version` (e.g., "v1.3.0-add-user-auth"), `branch_name` (sanitized)

3. **build-branch-frontend** (conditional)
   - Runs if: `needs.detect-changes.outputs.frontend_changed == 'true'`
   - Builds frontend Docker image
   - Tags: `ghcr.io/natosullivan/cuddly-disco/frontend:v1.3.0-add-user-auth`
   - Publishes to GHCR immediately (no semantic-release gate)

4. **build-branch-backend** (conditional)
   - Runs if: `needs.detect-changes.outputs.backend_changed == 'true'`
   - Builds backend Docker image
   - Tags: `ghcr.io/natosullivan/cuddly-disco/backend:v1.3.0-add-user-auth`
   - Publishes to GHCR immediately

5. **update-branch-helm-values** (new job)
   - Depends on: build-branch-frontend and/or build-branch-backend
   - Creates/updates Helm values files for changed apps
   - Commits to Git repository in `k8s/team-apps/*/values-dev-<branch-name>.yaml`
   - Uses `BOT_GITHUB_TOKEN` to trigger ArgoCD webhook

**Image Naming Convention**:
- Format: `ghcr.io/natosullivan/cuddly-disco/<app>:<version>`
- Example: `ghcr.io/natosullivan/cuddly-disco/frontend:v1.3.0-add-user-auth`
- Same version used for both frontend and backend from same branch

### 2. Helm Values File Management

#### Values File Generation

**Location**: `k8s/team-apps/<app>/values-dev-<branch-name>.yaml`

**Example**: `k8s/team-apps/frontend/values-dev-add-user-auth.yaml`

```yaml
# Auto-generated by GitHub Actions for branch: feature/add-user-auth
# Version: v1.3.0-add-user-auth
# Generated: 2025-11-21T10:30:00Z

version:
  name: "add-user-auth"        # Sanitized branch name (without v prefix)
  isDefault: false              # Never default - requires X-Version header

namespace:
  create: false                 # Reuse namespace from v1 deployment

image:
  repository: ghcr.io/natosullivan/cuddly-disco/frontend
  tag: "v1.3.0-add-user-auth"  # Branch-specific image tag

config:
  location: "Development (branch: add-user-auth)"  # Identifies branch in UI
  backendUrl: "http://backend-dev-add-user-auth-backend-app.backend.svc.cluster.local:5000"
  # ^^ Points to branch-specific backend if backend also changed, else default backend

resources:
  limits:
    cpu: 100m                   # Lower limits for branch versions
    memory: 128Mi
  requests:
    cpu: 50m
    memory: 64Mi
```

**Backend URL Logic**:
- If **both** frontend and backend changed: Point to branch-specific backend
- If **only** frontend changed: Point to default backend (`backend-dev-v1-backend-app`)
- If **only** backend changed: N/A (frontend doesn't need update)

#### Values File Lifecycle

**Creation**:
1. CI detects push to feature branch
2. Determines which apps changed
3. Generates values file(s) using template
4. Commits to Git with message: `chore: Add dev deployment for branch add-user-auth [skip ci]`

**Updates**:
1. Subsequent pushes to same branch
2. CI updates existing values file with new image tag (if image rebuilt)
3. Commits update: `chore: Update dev deployment for branch add-user-auth [skip ci]`

**Deletion**:
1. Branch merged or deleted
2. Cleanup workflow removes values file
3. Commits deletion: `chore: Remove dev deployment for branch add-user-auth [skip ci]`

### 3. ArgoCD ApplicationSet Configuration

#### Current ApplicationSet (for reference)

**File**: `k8s/argocd-appsets/team-apps.yaml`

Currently uses `matrix` generator with `list` elements for static versions (v1, v2).

#### Updated ApplicationSet (two approaches)

**Approach A: Git File Generator (Recommended)**

Automatically discovers values files using Git file glob patterns:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: team-apps
  namespace: argocd
spec:
  generators:
  - matrix:
      generators:
      # Discover all app directories (frontend, backend)
      - git:
          repoURL: https://github.com/natosullivan/cuddly-disco.git
          revision: HEAD
          directories:
          - path: k8s/team-apps/*

      # Discover all values files for dev environment
      - git:
          repoURL: https://github.com/natosullivan/cuddly-disco.git
          revision: HEAD
          files:
          - path: "k8s/team-apps/*/values-dev*.yaml"

  template:
    metadata:
      name: '{{path.basename}}-dev-{{path[2]}}' # e.g., frontend-dev-add-user-auth
      annotations:
        branch-version: "true"  # Mark as branch-based version
    spec:
      project: default
      source:
        repoURL: https://github.com/natosullivan/cuddly-disco.git
        targetRevision: HEAD
        path: '{{path[0]}}/{{path[1]}}/{{path.basename}}'  # k8s/team-apps/frontend
        helm:
          valueFiles:
          - values.yaml                    # Base values
          - '{{path[2]}}'                  # values-dev-add-user-auth.yaml
      destination:
        name: kind-dev
        namespace: '{{path.basename}}'     # frontend or backend
      syncPolicy:
        automated:
          prune: true                      # Auto-delete when values file removed
          selfHeal: true
```

**Git File Generator Parameters**:
- `path`: Glob pattern matching values files
- Expands to array: `[k8s, team-apps, frontend, values-dev-add-user-auth.yaml]`
- Can extract: `{{path.basename}}` = frontend, `{{path[2]}}` = values-dev-add-user-auth.yaml

**Pros**:
- Fully automated - no manual ApplicationSet updates
- Scales to unlimited branches
- Self-healing - adds/removes apps as values files change

**Cons**:
- Complex path template syntax
- Harder to separate branch versions from static versions (v1, v2)
- May need separate ApplicationSet for branch vs static versions

**Approach B: Hybrid with Separate ApplicationSets**

Keep existing ApplicationSet for static versions (v1, v2), create new one for branch versions:

**File**: `k8s/argocd-appsets/team-apps-branches.yaml` (new)

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: team-apps-branches
  namespace: argocd
spec:
  generators:
  - matrix:
      generators:
      # Discover app directories
      - git:
          repoURL: https://github.com/natosullivan/cuddly-disco.git
          revision: HEAD
          directories:
          - path: k8s/team-apps/*

      # Discover branch values files (exclude v1, v2 static versions)
      - git:
          repoURL: https://github.com/natosullivan/cuddly-disco.git
          revision: HEAD
          files:
          - path: "k8s/team-apps/*/values-dev-*.yaml"
            exclude: "k8s/team-apps/*/values-dev-v[0-9].yaml"  # Exclude v1, v2

  template:
    metadata:
      name: '{{path.basename}}-dev-{{branch}}'
      labels:
        app: '{{path.basename}}'
        environment: dev
        type: branch-version
    spec:
      # ... same as Approach A
```

**Pros**:
- Clean separation of concerns
- Easier to apply different policies (e.g., resource limits) to branch versions
- Existing static versions unaffected

**Cons**:
- Two ApplicationSets to maintain
- Slight duplication of configuration

**Recommendation**: Use **Approach B (Hybrid)** for cleaner separation and easier management.

### 4. Header-Based Routing

**No changes required** - existing HTTPRoute template already supports multi-version routing.

**Access Pattern**:
```bash
# Default version (v1)
curl http://dev.cuddly-disco.ai.localhost:3000

# Static version v2
curl -H "X-Version: v2" http://dev.cuddly-disco.ai.localhost:3000

# Branch version (add-user-auth)
curl -H "X-Version: add-user-auth" http://dev.cuddly-disco.ai.localhost:3000
```

**HTTPRoute Behavior**:
- Gateway API matches `X-Version` header to `version.name` value
- Routes to corresponding service: `frontend-dev-add-user-auth-frontend-app:3000`
- No header defaults to `isDefault: true` version (v1)

### 5. Cleanup Automation

#### Cleanup Workflow

**File**: `.github/workflows/cleanup-branch-version.yml` (new)

**Trigger**:
```yaml
on:
  pull_request:
    types: [closed]  # Merged or closed without merging
  delete:
    branches:
      - '*'
```

**Workflow Jobs**:

1. **determine-branch-name**
   - Extract branch name from PR or delete event
   - Sanitize using same logic as build workflow
   - Output: `branch_name` (e.g., "add-user-auth")

2. **detect-values-files**
   - Check if values files exist for this branch:
     - `k8s/team-apps/frontend/values-dev-<branch-name>.yaml`
     - `k8s/team-apps/backend/values-dev-<branch-name>.yaml`
   - Output: `frontend_exists`, `backend_exists`

3. **remove-helm-values**
   - Delete values files for this branch
   - Commit: `chore: Remove dev deployment for branch <branch-name> [skip ci]`
   - Uses `BOT_GITHUB_TOKEN` to trigger ArgoCD

4. **cleanup-images** (optional)
   - Delete container images from GHCR:
     - `ghcr.io/natosullivan/cuddly-disco/frontend:v1.3.0-<branch-name>`
     - `ghcr.io/natosullivan/cuddly-disco/backend:v1.3.0-<branch-name>`
   - Uses `gh api` or `docker` commands with GHCR API
   - **Note**: May want to keep images for audit/rollback purposes

**ArgoCD Behavior**:
- When values file deleted, Git file generator no longer matches
- ApplicationSet removes Application from cluster
- ArgoCD prunes all resources (Deployment, Service, ConfigMap, HTTPRoute)
- Cleanup completes within ~1-2 minutes of values file deletion

#### Manual Cleanup (backup method)

If automated cleanup fails, provide script for manual cleanup:

**File**: `infrastructure/cleanup-branch-version.sh` (new)

```bash
#!/bin/bash
# Usage: ./cleanup-branch-version.sh <branch-name>
# Example: ./cleanup-branch-version.sh add-user-auth

BRANCH_NAME=$1

# Remove values files
rm -f k8s/team-apps/frontend/values-dev-${BRANCH_NAME}.yaml
rm -f k8s/team-apps/backend/values-dev-${BRANCH_NAME}.yaml

# Commit changes
git add k8s/team-apps/*/values-dev-${BRANCH_NAME}.yaml
git commit -m "chore: Remove dev deployment for branch ${BRANCH_NAME}"
git push

echo "Cleanup complete. ArgoCD will prune resources within 1-2 minutes."
```

## Resource Management

### Resource Limits for Branch Versions

Branch versions should have lower resource limits than production:

```yaml
# values-dev-<branch-name>.yaml
resources:
  limits:
    cpu: 100m      # vs 200m in prod
    memory: 128Mi  # vs 256Mi in prod
  requests:
    cpu: 50m       # vs 100m in prod
    memory: 64Mi   # vs 128Mi in prod
```

### Quota Management

**Dev Cluster Quotas** (to prevent resource exhaustion):

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: branch-versions-quota
  namespace: frontend  # Apply to each namespace
spec:
  hard:
    count/deployments.apps: "10"    # Max 10 versions per app
    requests.cpu: "2"               # Total CPU requests
    requests.memory: "2Gi"          # Total memory requests
    limits.cpu: "4"                 # Total CPU limits
    limits.memory: "4Gi"            # Total memory limits
```

**Monitoring**:
- Alert when approaching quota limits
- Dashboard showing active branch versions
- Automated cleanup of stale versions (>7 days old, not updated)

## Future: Production Multi-Versioning

### Design Considerations

**Current State**:
- Prod has single version (v1) per app
- Manual promotion via `workflow_dispatch`

**Future State** (out of scope for initial implementation):

1. **Promotion Workflow**
   - Developer selects branch version to promote to prod
   - Creates `values-prod-<version>.yaml` files
   - Updates ApplicationSet to include prod branch versions
   - Requires approval (GitHub Environment protection rules)

2. **Prod Versioning Strategy**
   - Option A: Keep branch name (e.g., `v1.3.0-add-user-auth` in prod)
   - Option B: Promote to semantic version (e.g., v1.4.0) when merged
   - Option C: Hybrid - branch versions coexist with semantic versions

3. **Traffic Splitting**
   - Use Gateway API `weight` for canary deployments
   - Gradually shift traffic from v1 to v2
   - Automatic rollback on error rate increase

4. **Version Lifecycle in Prod**
   - Keep N versions (e.g., 3 most recent)
   - Automated cleanup of old versions
   - Blue/green deployment strategy

5. **Header-Based Access in Prod**
   - Same `X-Version` header pattern
   - Default version (no header) serves stable version
   - Other versions require explicit header

**Specification for prod multi-versioning should be created separately** once initial dev implementation is validated.

## Security Considerations

### Image Security
- Branch images should be scanned for vulnerabilities (same as main)
- Use same Docker build process as production
- No relaxed security policies for branch versions

### Access Control
- Dev environment accessible to all engineers
- Header-based routing doesn't provide security (anyone can set header)
- Use network policies if isolation required between versions
- Consider OAuth proxy for external access to dev environment

### Secrets Management
- Branch versions use same secrets as v1 (via Kubernetes Secrets)
- No branch-specific secrets unless explicitly required
- Audit log for secret access per version

### Resource Isolation
- Resource quotas prevent noisy neighbor problems
- NetworkPolicies can isolate traffic between versions
- Consider separate namespaces per branch if strong isolation needed

### Example CI Workflow Excerpt

```yaml
# .github/workflows/ci.yml (branch versioning section)

name: CI/CD Pipeline

on:
  push:
    branches:
      - main
      - '**'  # All branches
  pull_request:
  delete:

jobs:
  # ... existing jobs (frontend-tests, backend-tests) ...

  detect-changes:
    runs-on: ubuntu-latest
    if: github.ref != 'refs/heads/main'  # Only for non-main branches
    outputs:
      frontend_changed: ${{ steps.detect.outputs.frontend }}
      backend_changed: ${{ steps.detect.outputs.backend }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # Need full history for diff

      - name: Detect changed apps
        id: detect
        run: |
          git fetch origin main
          CHANGED_FILES=$(git diff --name-only origin/main...HEAD)

          if echo "$CHANGED_FILES" | grep -q '^apps/frontend/'; then
            echo "frontend=true" >> $GITHUB_OUTPUT
          else
            echo "frontend=false" >> $GITHUB_OUTPUT
          fi

          if echo "$CHANGED_FILES" | grep -q '^apps/backend/'; then
            echo "backend=true" >> $GITHUB_OUTPUT
          else
            echo "backend=false" >> $GITHUB_OUTPUT
          fi

  get-version-info:
    runs-on: ubuntu-latest
    if: github.ref != 'refs/heads/main'
    outputs:
      version: ${{ steps.version.outputs.version }}
      branch_name: ${{ steps.version.outputs.branch_name }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Generate version string
        id: version
        run: |
          # Get latest tag from main
          BASE_VERSION=$(git describe --tags --abbrev=0 origin/main || echo "v0.0.0")

          # Extract and sanitize branch name
          BRANCH=${GITHUB_REF#refs/heads/}
          BRANCH=${BRANCH#feature/}
          BRANCH=${BRANCH#bugfix/}
          BRANCH=${BRANCH#hotfix/}
          BRANCH=$(echo "$BRANCH" | sed 's/[^a-zA-Z0-9-]/-/g' | sed 's/--*/-/g' | tr '[:upper:]' '[:lower:]')

          VERSION="${BASE_VERSION}-${BRANCH}"
```
